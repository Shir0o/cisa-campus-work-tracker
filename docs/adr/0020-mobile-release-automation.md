# 0020. Mobile release automation: tag-driven local EAS builds

Date: 2026-09-13

## Status

Accepted

## Context

Releasing the mobile app was entirely manual. `eas.json` already carried
store-bound profiles and `--auto-submit` npm scripts, but nothing ran them: no
tag was cut for the app, no CHANGELOG existed under `apps/mobile`, and no
workflow touched EAS. The `APP_STORE_RELEASE_CHECKLIST.md` described archiving
in Xcode and running a Gradle build by hand — steps that no longer exist in this
repository, because `ios/` and `android/` are **untracked** and generated by
`expo prebuild` (Continuous Native Generation). The documented process had
drifted away from the tooling.

The sibling repository `Shir0o/bible-read` had solved the same problem for a
Flutter app: release-please owns the version, the tag drives the build, and the
upload to the store is automated while promotion stays a human click. The
question was whether that *shape* transfers to an Expo/EAS project, and which
parts of its *mechanism* must change.

Three constraints shaped the answer:

1. **A macOS build is unavoidable for iOS**, and EAS's cloud build minutes are
   metered against the Expo plan. The repository is **public**, so GitHub-hosted
   runners — macOS included — are free and unmetered. Building on the runner is
   therefore cheaper than building on EAS.
2. **`cli.appVersionSource` is a project-wide setting.** It is not per-command
   and not per-machine. Whatever is chosen governs `eas build` (cloud),
   `eas build --local` (a developer's machine), and CI identically. A scheme that
   only held in CI would let a local build mint a duplicate build number.
3. **`eas build` has no `--build-number` flag.** Its full flag list is:
   `platform, skip-credentials-check, skip-project-configuration, profile, local,
   output, wait, clear-cache, auto-submit, auto-submit-with-profile,
   what-to-test, resource-class, message, build-logger-level, freeze-credentials,
   refresh-ad-hoc-provisioning-profile, verbose-logs`. A tag-derived build number
   can therefore only enter through `app.json`.

## Decision

1. **release-please, scoped to `apps/mobile`, drives tags.** The repository is a
   monorepo whose web app deploys on merge to `main`; an unscoped release-please
   would cut mobile releases for web-only changes and fork the app's runtime
   version. `include-component-in-tag: false` keeps tags as `v1.4.0`, matching
   bible-read.
2. **The tag is the single source of truth for both version and build number.**
   `scripts/mobile-version.ts` derives `major*10000 + minor*100 + patch` and
   writes `expo.version`, `expo.ios.buildNumber`, and `expo.android.versionCode`
   into `apps/mobile/app.json`. CI and a developer's machine run the same script,
   so they cannot disagree.
3. **`autoIncrement` is removed from every profile.** With a local version
   source, `eas build` bumps the build number by *editing `app.json` on disk*
   (`bumpAppVersionAsync` → `updateAppJsonConfigAsync`, with
   `localAutoIncrement: true` passed to `syncProjectConfigurationAsync`). Leaving
   it on would fight the tag, dirty the working tree, and let two machines mint
   the same number.
4. **Builds run on GitHub runners via `eas build --local`.** No EAS cloud build
   minutes are consumed, and CI, cloud, and a laptop all execute the same
   pipeline — the `--local` path only changes *where* the job runs
   (`runLocalBuildAsync` hands it to `eas-cli-local-build-plugin`), never how
   versions or credentials resolve. The CLI marks `--local` **experimental**;
   this is accepted and recorded here.
5. **Credentials are repo-managed** (`credentialsSource: "local"`), downloaded
   once with `eas credentials` and packed by `scripts/pack-eas-credentials.ts`
   into a single base64 secret. `credentials.json` is a *pointer* file - it names
   the Android keystore and the iOS `.p12` and `.mobileprovision` - so the secret
   has to carry the whole set, not just the JSON.
6. **`eas submit` reaches the Play internal track and TestFlight, and stops.**
   No `--auto-submit`, no promotion. Play uses `releaseStatus: draft` so internal
   testers are not notified.
7. **The `testflight` profile is collapsed into `production`** (they were
   functionally identical), and **`qa` becomes a non-store build** — internal
   distribution, APK, still pointed at `qa-db` — so `production` is the only
   profile that reaches a store.
8. **Store notes are compiled from `content/whats-new/`** rather than authored
   twice, per ADR 0008. Play caps a changelog at 500 characters; the script
   enforces it.
9. **The release jobs sit behind a protected `mobile-release` environment.** On a
   public repository anyone can open a PR, so the environment gate — not the tag
   — is what stands between a merged PR and both stores.

## Alternatives considered

- **EAS cloud builds orchestrated by GitHub Actions.** Simplest pipeline, and it
  would have collapsed store credentials to roughly one secret, since EAS would
  manage signing. Rejected: metered build minutes against a plan, when free
  unmetered macOS runners are available on a public repository.
- **Raw `expo prebuild` + `gradlew bundleRelease` + `xcodebuild archive`.**
  Cheapest, and already proven for Android by `mobile-e2e.yml`. Rejected for
  iOS: it means owning `ExportOptions.plist`, profile matching, and
  archive/export — the most failure-prone part of an iOS release — and it would
  diverge from what a developer's `eas build --local` produces.
- **Keeping `appVersionSource: "remote"`.** EAS would guarantee unique build
  numbers from server state, and `autoIncrement` would never touch the tree.
  Rejected: the build number would live on Expo's servers rather than in git, so
  `v1.4.0 -> 10400` would stop being reproducible from a tag.
- **EAS's native GitHub integration or `.eas/workflows/`.** Removes the workflow
  files entirely. Rejected: it is not a GitHub Action, the release needs to
  coordinate with a monorepo whose web half already deploys from Actions, and it
  would reintroduce metered cloud builds.
- **Adding OTA updates (`eas update`).** Rejected for now: no profile sets a
  `channel`, so over-the-air updates cannot work today, and enabling them would
  couple the marketing version to `runtimeVersion` under the current `appVersion`
  policy.

## Consequences

### Positive

- One merged PR ships to both stores; the operator only promotes.
- Nothing in CI consumes EAS build minutes, and GitHub runner minutes are free
  on a public repository.
- `v1.4.0` on GitHub, `1.4.0` in `app.json`, `10400` on both stores, and the
  whats-new manifest all agree by construction.
- Store release notes have one source of truth instead of two.

### Negative

- Six GitHub secrets to provision and rotate, and the annual iOS certificate
  expiry is now ours rather than EAS's.
- `--local` is flagged experimental upstream; it is the only build path CI uses.
- `apps/mobile/package.json` now carries a release version it never had before
  (`0.1.0` -> `1.3.8`), because release-please needs a version file to bump.
  Web and mobile therefore version independently — deliberate, but it is a new
  thing for a contributor to learn.
- **Play release notes need a second tool.** `eas submit` has no field for them,
  so `release-android.yml` runs fastlane `supply` afterwards with
  `skip_upload_aab: true` to attach the changelog to the version `eas submit`
  already placed on the track. That means Ruby and a `Gemfile` in the Android
  job for the sake of one metadata field. TestFlight needs none of it -
  `--what-to-test` carries the notes.

### Reversibility

- **Easy**: the workflows, the release-please config, and the two scripts are
  each removable in one commit.
- **Medium**: `appVersionSource: "local"` plus a tag-derived build number can be
  returned to `remote`, but every build number issued in the meantime stays
  spent, and Apple never accepts a reused `CFBundleVersion`.
- **Hard**: the Play upload key and the App Store Connect API key, once enrolled,
  retain store access until revoked by hand.

## Known conflict

Three different versions were in flight when this ADR was written: the newest tag
`v1.3.8`, `apps/mobile/app.json` at `1.0.1`, and `content/whats-new` at `1.4.0`.
The manifest baseline is set to `1.3.8` — the newest tag — so the first automated
release bumps from there. **Reconcile the whats-new version and confirm what the
stores actually have before the first automated release**, or App Store Connect
will reject a `CFBundleShortVersionString` at or below the last approved build.

**Partly resolved:** the two overlapping "what's new" systems were
reconciled by [ADR 0024](0024-one-release-record-two-registers.md); the
release record is now the one authored source. Version truth (the tag vs
`app.json` vs the record) is owned by issue #1020.
