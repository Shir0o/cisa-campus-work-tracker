The feed becomes a worklist

A Full-timer needs the contacts Trainees add to behave like an inbox — the ones I have looked at, and the ones that are new — without losing the ones opened and deliberately left for later. That is two facts, not one, and the code already models them as two: userEntityState.ts defines read as “seen / scanned” and done as “cleared / handled”. They are in localStorage, and the feed collapses them into one gesture. This separates them and moves them to the server.

One column, one list

Not a new page, and not History

The worklist is the column that is already there — you already go to it and click the comment icon. A second destination is a second place to keep clean, and the orphaned FromTraineesInbox.tsx (exported, imported nowhere) is what happens when one gets built and forgotten.

History cannot be the home. It reads the activities collection — a separate audit log, limit(100) team-wide — which shares no item identities with the feed. Marking a row viewed there could never make the feed agree, so you would keep two viewed-states over two records of the same events.

New people sort first. That is a sort, not a second list — splitting contacts out means deciding, every time, where the things that are neither go.

lib/inbox.ts and FromTraineesInbox.tsx are deleted on web. Mobile still uses inboxItemsFor and keeps it until the two derivations are unified.

Two facts, kept apart

The whole point: opening something must never make the number go down. Today one click does both, which is why an inbox built on it would lie.

Seen

Passive. You opened the contact, so you know who this is. Set only by opening — never by scrolling past, and never by “Mark all seen” claiming you reviewed anyone.

Shows as the accent dot beside the name. Gone once you have opened them.
Set by opening the contact — the card’s name or Open.
Never set by the card scrolling into view. Nothing in AttentionFeed does this today and nothing should start.

Completed

Deliberate. You are finished with this item. This is the number in the header — “8 to work through” counts everything not completed, seen or not.

Shows as the card greying in place with an Undo — it clears when you leave, not under your cursor.
Set by a button whose words fit the item — see below.
Opened but not completed is a real state — you looked, it needs more from you, it stays in the count.

The words, per item

“I followed up” on a card about a note claims you texted the student, which you did not. Three families of verb: things you look at, things you owe someone, and things that are only information.

The finding that forces the server — and the one that makes it cheap

contact.reviewed exists, is documented as “whether the full-timer walking with the adder has reviewed this contact”, is read in four places — and is written by nothing but the seed scripts. It has been undefined on every real contact since it was added, so the viewed axis has always fallen through to localStorage: mark ten people reviewed on your laptop, open your phone, all ten are new again.

It cannot simply be turned on, either. One boolean on a shared document means somebody reviewed it — with several Full-timers, the first to look clears it for everyone. And writing per-person state onto the contact makes every glance a write to a document twelve clients are subscribed to. The state belongs to the person, so it lives with the person: one document at inboxState/<uid> holding the two id sets, under a rule that already exists in the same shape for userPreferences/<uid>.

Migration is a copy

userEntityState.ts already migrates three legacy stores on first load. Do the same one level up: first load with no server document uploads the local sets, then the server is authoritative. Starting clean would show every Full-timer their whole contact history as New on launch day — the worst possible first impression of an inbox.

Who gets it

Both roles. A Trainee with four open questions needs the count more than a Full-timer does — less time in the app, more chance of missing something. inboxItemsFor no-ops for non-Full-timers by design, but that guard was about oversight of the team, which is genuinely Full-timer-only. A personal worklist is not.

Growth, and the one real cost

Roughly 170 items per person per term. A document of ids is fine for years, but unbounded is a smell — prune ids older than a term on write. And the copy is hardcoded English, like the rest of AttentionFeed: every string here goes through en.json and es.json or npm run check:i18n fails.
